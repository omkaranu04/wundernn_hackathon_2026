# Timing / size correlations across submitted experiments

Generated by `analysis/scripts/compute_timing_correlations.py`. Source figures transcribed from `EXPERIMENTS.md` (each independently documented there) plus params/nodes computed directly from each experiment's `checkpoints/model.onnx` / `best.pt`.

**All `local_wp`/`platform_wp` values below are under the corrected ("Global") WP metric the organizers switched to on 2026-09-15/16**, not the original per-sequence-averaged metric - see `EXPERIMENTS.md`'s "Metric correction" section and `PROBLEM_STATEMENT.md` §3 for what changed. This note exists because this file's own timing/latency figures ("uncorrected" in every mention below) refer to a completely different thing - the local synthetic latency estimate *before applying the platform's speedup factor* - and the two senses of "corrected"/"uncorrected" in this document should not be conflated with each other.

## The headline finding: valid.parquet and the hidden test set are NOT the same size

Every experiment's "% of budget uncorrected" figure in this project comes from `budget = 60*60*1000/37274573` (present verbatim in every `auto_pipeline*.sh`). That denominator, 37,274,573, is exactly `1873 valid sequences x 19901 predict-needed steps/sequence = 37,274,573` - i.e. **the budget formula silently assumes the hidden test set is the same size as valid.parquet.**

It isn't: the FAQ documents the real test set at **1970 sequences** (39,204,970 predict-needed steps, assuming the same 99-step warmup), which is **5.18% more** steps than valid.parquet. Since total platform wall-time scales with total steps at a roughly fixed per-step rate, every uncorrected latency percentage quoted throughout this project's history **understates the real test-set time by ~5.2%** purely from this size mismatch, before any platform-speedup effects are even considered. A model benchmarked at exactly 100.0% uncorrected is actually looking at ~105.2% of true budget on the real test set.

**Practical takeaway: treat the existing safety margins as ~5% thinner than they look.** The project's own empirical safe/risky boundary (next section) already has enough slack that this doesn't overturn any past decision, but it's worth folding into the benchmark script directly (multiply the reported %% by 1.0518) rather than re-deriving it by hand each time.

## Local uncorrected latency %% vs. actual platform runtime

Pearson r = **0.927** (n=91 scored submissions, excludes timeouts since their runtime is censored at the ~4200s hard kill, not a true completion time).

The relationship is real but **not a fixed multiplier** - the implied platform speedup factor (`local_lat_pct / actual_runtime_pct`) ranges from as low as **0.87x** (004's original 5-epoch submission, the one confirmed case of the platform running slower than the local estimate) up to **1.59x** (002's and 012's first submissions), and even varies **within the same architecture and weights**: 002's identical extended-retrain zip got 1.59x on 2026-09-13 but only ~1.10x on its 2026-09-17 resubmit (timed out), then scored fine on a second resubmit. So the correlation should be read as *directionally predictive, not quantitatively precise* - useful for ranking risk across experiments, not for computing a guaranteed runtime.

**Empirical safe/risky bands observed across all 33 submissions logged here:**

- **<=125% uncorrected: every submission scored.** (003 91.3%, 004 89.6-95.6%, 006 88.5%, 008 90.4%, 009 90.6%, 010 100.5%, 011 122.9%, 012 112.2%, 013-priceonly 118.3%, 017 123.6%, all scored.)
- **~125-136%: gray zone, but not a cliff.** 002 at 127.7% has landed on both sides across three submissions of the exact same zip (scored at 48m25s, timed out at 69m59s, scored at 53m54s), and 018 at 135.6% scored at 54m7s (90.2% of budget, implied platform speedup 1.50x) - the highest-latency submission to clear so far, with only ~6 minutes of margin.
- **>=180% uncorrected: every submission timed out, no exceptions.** (013-original 179.9%, 001-full 233.5%, 015 235.5%, 014 356.4%, 016 387.3%.) Even this project's best-ever observed speedup (1.59x) wouldn't be enough to rescue anything above ~160% uncorrected. The band between 136% and 180% is still untested.

## What drives the local uncorrected latency %% itself

- ONNX node count vs. latency %%: Pearson r = **0.845** (n=94)
- Parameter count vs. latency %%: Pearson r = **0.179** (n=95)
- Parameter count vs. node count: Pearson r = **-0.248** (n=103)

Node count is the tighter predictor, consistent with this project's repeated finding (004/009/012/013/016) that ONNX Runtime latency tracks *op/graph structure*, not FLOPs or parameter count directly - 013's own fix history is the cleanest single illustration: the exact same parameter count (246,334) went from 128 nodes/179.9%% to 58 nodes/118.3%% purely by restructuring the graph (vectorizing a Python-loop EWMA update, then narrowing its scope), with zero change to how many weights the model has. **When estimating a new architecture's latency risk before training, sketch the ONNX node count (or count nodes on a random-init export) rather than reasoning from parameter count or FLOPs - it's the more reliable early signal.**

## Does model size correlate with accuracy (WP)?

- Node count vs. platform WP: Pearson r = **-0.355** (n=98)
- Parameter count vs. platform WP: Pearson r = **0.430** (n=99)
- Node count vs. local WP: Pearson r = **-0.044** (n=30)

Weak-to-moderate, and almost certainly not causal: node count correlates with WP more than raw parameter count does, but that's consistent with node count being a proxy for "has a richer feature encoder" (004's grouped encoder: 43 nodes; 012/017's 5x nonlinear expansion: 62/71 nodes) rather than nodes themselves improving accuracy - the encoder-design choice drives both numbers together. The clearest evidence it isn't node count per se: 011 (233,194 params, same backbone as 004/010) has the worst platform WP in the fleet (0.6305) despite an unremarkable node count, because its extra complexity went into a separately-optimized XGBoost head that never improved accuracy; and 014/015/016 (105-198 nodes, the fleet's highest) cluster at 0.678-0.683 local WP - no better than 012/017's 62-71-node encoders, and worse on latency. **The practical read: spend node-count budget on feature/encoder richness (004's grouping, 012's nonlinear expansion), not on backbone depth/width or attention mechanisms - the former has paid off in this project's history (WP), the latter has only cost latency margin without a demonstrated accuracy payoff.**
