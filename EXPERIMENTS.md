### ⚠️ Metric correction (2026-09-15/16) — read before trusting any number below

The organizers found a mistake in their original WP calculation and
**re-evaluated every one of our submissions** under a corrected metric.
Full spec change: `PROBLEM_STATEMENT.md` §3. Short version:

- **Old metric**: compute one weighted-Pearson value *per 20,000-row
  sequence*, then average those values equally across all eligible
  sequences (a sequence with 100 scored rows counted the same as one with
  10,000; sequences without both a positive and negative clipped target
  were excluded entirely).
- **New ("Global") metric**: pool every selected row from every sequence
  into ONE global weighted-Pearson calculation per target, then average
  the two targets. No per-sequence averaging, no apparent per-sequence
  eligibility exclusion.

**This reordered our results.** Under the old metric, experiment 005 was
our best platform score (0.6108) and experiment 002 second (0.6106). Under
the corrected metric, **004 and 002 are now essentially tied for best**
(0.6508 / 0.6507) and **005 dropped to near the bottom** of the
post-baseline cluster (0.6473) — see the updated table below. Runtimes and
memory are unaffected (re-scoring doesn't re-run inference); only the WP
numbers changed.

**RESOLVED (2026-09-16): local scoring is fixed.** It turned out the
organizers had already updated `wnn_connectome_starterpack/utils.py` on
disk to implement the corrected metric (`GlobalAccumulator` replacing the
old `BlockAccumulator`, confirmed via `git diff` against the originally
committed version) — we just hadn't re-checked it. All 7 pre-existing
experiments (001-007) plus the new experiment 008 have been re-scored
locally under the corrected metric (`rescore_all_global.sh`, completed
2026-09-16 10:34) — every "Local WP" value in the table below is now the
corrected, trustworthy number. The corrected local ranking now agrees
with the corrected platform ranking at the top (002 is best on both).

### Cross-experiment timing/size analysis (2026-09-24)

With 21 platform submissions logged as of 2026-09-24 (updated 2026-10-10: 22nd = experiment 018, 23rd = 019's pooled60, 24th = 022 arm 1, 25th = 024's GRU, 26th-29th = the four 026/027 zips, 30th = 001-d32, 31st-33rd = 028's A/B/C), ran a correlation pass across every submission's params, ONNX node count, local uncorrected latency %, and actual platform runtime — `analysis/scripts/compute_timing_correlations.py`, results in `analysis/results/timing_correlations.md`/`.csv`. Highlights:

- **The "budget" formula itself has a ~5.2% blind spot.** `budget = 60*60*1000/37274573` (in every `auto_pipeline*.sh`) divides by valid.parquet's step count (1873 sequences × 19901 = 37,274,573), not the real hidden test set's (1970 sequences × 19901 = 39,204,970, per the FAQ). Every "% of budget uncorrected" figure quoted throughout this project therefore understates true test-set time by ~5.18% — a model benchmarked at exactly 100.0% is really looking at ~105.2% on the real test set. Doesn't overturn any past decision (existing margins already have enough slack), but worth folding into the benchmark script going forward.
- **Local latency % vs. actual platform runtime: r=0.635** (scored submissions only, n=31 as of 2026-10-12, 37 submissions in the table; was 0.514 before 018 and 019-pooled60 were added) — real but not a fixed multiplier; the implied speedup factor has ranged 0.87x-1.59x, including within the *same* architecture/weights across resubmits (002's identical zip: 1.59x → ~1.10x → scored). Empirically: **≤125% uncorrected has scored every time (n=11); ≥180% has timed out every time, no exceptions (n=5); 125-136% is a gray zone, not a cliff** — 002 (127.7%) has landed on both sides across its three submissions, and 018 (135.6%) scored at 54m7s (90.2% of budget, implied speedup 1.50x), the highest-latency submission to clear so far. The 136-180% band is still untested.
- **ONNX node count predicts local latency % far better than parameter count does**: r(nodes, latency%)=0.918 vs. r(params, latency%)=0.542, and r(params, nodes)=0.256 — params and nodes are fairly decoupled. 013's own fix history is the cleanest illustration: identical 246,334 params, 128→58 nodes via pure graph restructuring, 179.9%→118.3% latency. **When gauging a new architecture's risk before training, count/estimate ONNX nodes, not params or FLOPs.**
- **Node count has only a weak-to-moderate link to WP** (r=0.325 platform, n=25) and it isn't causal — it's a proxy for "richer feature encoder" (004's grouping, 012's nonlinear expansion both add nodes AND accuracy together), not evidence that more nodes helps by itself. 011's XGBoost head (worst platform WP in the fleet) and 014/015/016's attention variants (fleet-worst latency, no local-WP edge over 012/017's simpler encoders) both show extra complexity without an accuracy payoff. **Practical implication for future experiments: spend node-count budget on feature/encoder design, not backbone depth/width/attention — the former has a demonstrated track record in this project, the latter has only cost latency margin.**

### Recurrent-state reset diagnostic (2026-10-08, experiment 020, no training)

Tested whether periodically zeroing the LSTM state (an idea from another competition) could help us. On 004 and 012's trained weights (full valid set, corrected global WP): WP is flat across the 20,000-step sequence (no drift), and resetting at inference made WP monotonically worse the more often it was applied (004: -0.0003/-0.0007/-0.0023 at N=10000/5000/2000; 012: -0.0003/-0.0004/-0.0014). ### Scored-row structure (2026-10-09, analysis only; idea under discussion, nothing built)

Motivated by a competitor-analysis idea: the metric pools only a hidden subset of rows (`is_scored`), so concentrate the training loss on rows likely to be scored. Facts verified on our data (`analysis/scripts/scored_rows_probe.py`):
- **Labels exist only for validation**: `valid.parquet` has `is_scored`, and `valid_mask.parquet` carries `seq_ix, step_in_seq, is_scored`. `train.parquet` has no scoring flag, so any mask for train must be predicted.
- **~10.2% of `need_prediction` rows are scored** (3,528,273 of 37.27M overall), every sequence has some, in short scattered runs (mean length 4.0, median 2, p90 8, max 748; ~500 runs per sequence), spread over the whole sequence (position quartiles 0.25/0.47/0.73).
- **Scored rows have larger targets** (mean |t| 0.73 vs 0.60) but similar exact-zero fractions (~22%); |t0|+|t1| alone barely separates them (AUC 0.53), so selection is not mainly target-driven.
- **The mask is highly predictable from the features alone**: a gradient-boosting classifier on the 112 features + step-to-step differences (no targets), trained on 50 valid sequences (300K sampled rows), reaches **held-out AUC 0.859, average precision 0.42 vs. a 0.085 base rate** on 20 unseen sequences. A stronger non-causal model on all 1,873 labelled sequences should do better.
- **012 correlates far better on scored rows**: corrected WP on 24 valid sequences is 0.670 on scored rows vs 0.468 on unscored rows and 0.497 on all `need_prediction` rows. Scored rows are a distinct, more predictable regime, and our current loss weights every row equally, so ~90% of its weight goes to rows the metric ignores.
**Update 2026-10-09: the mask predictor was built (experiment 025): held-out AUC 0.952, AP 0.728, calibrated, train fully labelled.** The weighted-loss training run was launched 2026-10-09 as experiment 026 (weighted arm + same-code control). Original proposal: train a non-causal mask predictor on a labelled split of valid (report held-out AUC/AP), label train.parquet with soft probabilities, and weight BOTH the MSE and Pearson terms per row by p x |clipped target|, keeping 012's architecture, recipe and WP-based selection with the true valid mask; if it underperforms, retry with a floor-plus-probability weight. Treat differences under ~0.004 as unresolved.

### Policy: never target the platform's observed grace period

Experiments 004 and 005 both exceeded the nominal 60-minute limit (61m32s,
61m34s) and both still scored — confirming some tolerance exists beyond
the stated cutoff. **We will not design or knowingly submit anything that
depends on that tolerance.** The observed buffer is small (~1.5-2 minutes
on 2 data points), undocumented by the organizers, and could differ by
test-set size, load on the scoring infra, or simply not be guaranteed
behavior. Future experiments should continue targeting genuine margin
under 60 minutes (per the existing "uncorrected synthetic estimate <100%,
ideally <90-95%" guidance), not a number that happens to work because of
an unstated grace period.

**Hardened 2026-09-17: the platform's speedup factor is not a fixed
property of an architecture — it can change between submissions of the
exact same model.** Experiment 002's extended-training resubmission
(2026-09-17, ID 0BGLDK10) used the byte-identical ONNX graph (only the
weights changed via retraining, same node count/structure) as the
original 002 submission (2026-09-13, ID 1C8UCKOX). The original got a
1.59x platform speedup and ran safely at 48m25s. The resubmission got
only ~1.095x and **timed out at 69m59s — no score at all**, burning a
submission slot. Since the architecture was identical, this speedup
difference has to be platform-side (load, scoring-infra conditions, or
similar) rather than anything about our model. **Practical implication:**
a config that has previously scored successfully on the platform is
*still not proven safe* for a future resubmission if its uncorrected
synthetic latency was ever above ~100% (i.e. it needed *any* speedup
factor to fit) — only genuinely <100% (ideally <90-95%) uncorrected
configs should be treated as safe to resubmit with confidence.

**Explicitly not worth retrying without a new angle** (ruled out with
reasonable confidence by the fleet so far): more LSTM depth or width alone;
windowed/sparse self-attention at d_model=128 scale; a two-stage
tree-ensemble head; the `sinh` output activation. Any future variant on
these would need a specific reason to expect a different outcome, not just
a parameter tweak.

**Operational reminders baked in from this project's submission history**
(see the timing-correlation and grace-period sections above for the full
evidence): target ≤~110-115% of budget uncorrected (not just ≤100%) to
leave room for the newly-found ~5.2% valid/test size gap and for the
platform's observed ±0.87-1.59x speedup variance; estimate latency risk
from ONNX node count, not parameter count; never design toward the
platform's observed timeout grace period; and local WP ranking has
mismatched platform WP ranking more than once (010, 017) so a close local
call is not a reliable tiebreaker on its own.

## Conventions

- Each experiment lives in `experiments/NNN_short-name/` — never edit a past experiment's code after moving on; start a new numbered dir instead, even for small tweaks, so history stays intact.
- Each experiment dir should have its own `README.md`: what was tried, why, what changed vs. the previous experiment, and the result.
- Code shared across experiments (data loading, feature prep, common training utilities) goes in `shared/`, imported by experiment scripts — don't copy-paste it into every experiment folder.
- Anything actually uploaded to the platform gets archived into `submissions/` (the exact zip, or the exact solution.py + artifacts), named `NNN_short-name_YYYY-MM-DD.zip`, and logged in the table above with the real leaderboard score once known.
- `wnn_connectome_starterpack/` is vendor-provided — treat it as read-only reference; don't edit data/docs files in there (the earlier `tqdm` addition to its `utils.py` is the one intentional local-dev exception).
